# Подключение клиента

Как подключить базу к клиенту MCP: Claude (веб, десктоп, телефон), Claude Code, любой другой клиент, голый curl.

## Люди: OAuth

В Claude: Settings, Connectors, Add custom connector, URL `https://your-domain/mcp`. Откроется окно GitHub/Google, вход под аккаунтом из `MCP_ALLOWED_USERS`. После этого все 15 инструментов доступны из чата и с телефона.

В Claude Code и других клиентах с HTTP-транспортом:

```json
{
  "mcpServers": {
    "vault": {
      "type": "http",
      "url": "https://your-domain/mcp"
    }
  }
}
```

Клиент сам проведет OAuth-танец.

Замечание про адрес: `/mcp` без слеша на конце. Со слешем (`/mcp/`) некоторые клиенты ловят редирект 307, а самописный curl без `-L` нет.

## Машины: статический токен

Токен выдан заранее (см. [static-tokens.md](static-tokens.md)). Никакого браузера: обычный заголовок Authorization.

```json
{
  "mcpServers": {
    "vault": {
      "type": "http",
      "url": "https://your-domain/mcp",
      "headers": {
        "Authorization": "Bearer ${VAULT_MCP_TOKEN}"
      }
    }
  }
}
```

Клиенты раскрывают `${VAR}` из окружения процесса. Сам токен лежит в файле 0600 вне git и попадает в окружение командой вида `export VAULT_MCP_TOKEN="$(cat /path/to/token-file)"`.

Проверка руками, без всякого клиента:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST https://your-domain/mcp \
  -H "Authorization: Bearer $VAULT_MCP_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}'
# 200 = токен принят; 401 = отклонен
```

Полный сценарий (создание заметки, правка, отказы по политике): `python tools/probe_static_token.py`.

## Что видно в ответах

| Ситуация | Ответ | Что это значит |
|---|---|---|
| Токен принят | обычная работа инструментов | ничего |
| Токена нет, неизвестен, отозван, просрочен | HTTP 401 `invalid_token` | причина в `mcp-auth.jsonl` на сервере (`unknown` или `expired`); не перезапускать сессию в цикле, спросить владельца |
| Инструмент запрещен политикой | `ERROR: tool 'delete_note' is denied for user 'agent'` (HTTP 200) | это ответ инструмента, а не транспорта; обходить не нужно: удаление это решение человека |
| `MCP_READONLY=true` у сервера | `ERROR: server is read-only (MCP_READONLY)` | инцидентный режим у владельца, ждать |
| `readonly` в строке учетки | `ERROR: server is read-only for user '…'` | владелец сделал учетку только читающей |

Каждый мутирующий вызов (включая отказы) попадает в журнал владельца `mcp-writes.jsonl` с именем учетки. Это атрибуция, а не наказание: владелец видит, что сделала машина, а что человек.

## Ротация и отзыв

Все это правки одной строки в файле хешей на сервере, действуют со следующего запроса, клиент ничего не делает:

- смена токена: выдать новый (`tools/issue_token.py`), заменить строку, положить новый токен в файл клиента;
- отзыв: удалить строку, клиент получает 401;
- срок: дата в строке это первый день недействительности (UTC), новый токен стоит выдать за неделю до нее;
- права: пятое поле строки (`deny=…` / `readonly`).

## Чего делать не нужно

- Не передавать машине токен человека и не «одалживать» OAuth-сессию: пропадает атрибуция и границы.
- Не хранить токен в `settings.json` или `.mcp.json` открытым текстом: файл 0600 плюс переменная окружения.
- Не печатать токен в логах и транскриптах: показанный один раз секрет считается скомпрометированным, лечится только выдачей нового.
